# 最高等級鑽石引擎：研究與決策驗證系統

## 一、最高治理原則

### 1. 正式策略不得由 AI 自行修改

AI 可以：

- 蒐集案例。
- 建立候選池。
- 進行測試與回測。
- 比較備案。
- 建立 Proposal。
- 說明改善、惡化、風險與適用市場。

AI 不可以：

- 自行修改正式 Pine 程式。
- 覆蓋既有版本。
- 自行變更 Stable。
- 自行合併正式分支。
- 因單一案例直接調參數。
- 未經討論就把測試結果套入正式策略。

固定流程：

```text
發現問題
→ 留存案例
→ 統計與分類
→ 建立一個或多個備案
→ 使用相同樣本與相同成本假設測試
→ 保存基準版與測試版結果
→ 與使用者討論
→ 使用者明確批准
→ 才能製作下一個正式版本
→ 再經驗證後才可升為 Stable
```

此原則高於自動學習、自動進化、自動放寬及永遠使用最新版等所有規則。

## 二、系統角色

### 鑽石引擎

負責基本面、法人、資金流、融資融券、產業鏈、市場情緒與一般個股研究。

### 波段研究室

負責：

- 全市場選標。
- 同族群比較。
- 為什麼選 A、不選 B。
- 記錄每個候選的優點、缺點與淘汰原因。
- 記錄計畫進場價、實際進場價、停損、目標、信心、成熟度。
- 持續追蹤至出場。
- 記錄獲利率、持有天數、MFE、MAE、出場原因與事後檢討。

### Engine Lab

負責：

- 每日以多排行榜建立 50 至 100 檔當沖候選池。
- 所有正式訊號以最新 Stable 台股引擎 TradingView 版本為準。
- 比較 AI 預期與 TradingView 實際結果。
- 分類漏訊、假訊、共識訊號與共識無訊號。
- 記錄造成訊號成立或被否決的實際 Gate Trace。
- 建立可驗證的改版備案，但不得自行修改正式程式。

## 三、波段 Decision Journal

每一筆波段決策使用唯一 ID：

```text
SWING-YYYYMMDD-NNN
```

必須保存：

- 日期、股票、名稱、族群。
- 候選排名、波段分數、信心、成熟度。
- 是否入選。
- 為什麼選擇。
- 為什麼淘汰。
- 同族群比較資料。
- 基本面、法人、量價、EMA、斐波、題材、市場情緒、風報比證據。
- 計畫進場、實際進場、停損、目標。
- 實際出場、持有天數、報酬、MFE、MAE。
- 出場原因。
- 原判斷正確與錯誤之處。
- 下次遇到相同情境應如何處理。

### 同族群比較原則

不能只記錄選了誰。必須回答：

- A 相較 B 的優勢是什麼？
- B 被淘汰的真正原因是什麼？
- A 的缺點是什麼？
- 是否存在原候選以外更好的標的？
- 最終結果是否證明當初選擇正確？

若未選標的後續表現更好，必須承認並記錄原判斷失誤，不能事後改寫理由。

## 四、當沖 Candidate Pool

每日候選池建議由多個排行榜組成，去重後控制在 50 至 100 檔：

- 成交值排行。
- 成交量排行。
- 漲幅／跌幅排行。
- 波動率與振幅排行。
- 外資、投信買賣超排行。
- 量增排行。
- 早期轉強排行。
- 市場主流族群與異常強弱股。

不得只使用單一成交值排行，避免樣本偏誤。

每次候選池必須保存：

- Pool ID。
- 交易日。
- 候選來源。
- 去重後排名。
- 股票數量。
- 使用的 Stable 引擎版本。
- 選取與排除規則。

## 五、Engine Lab 案例分類

### False Negative／漏訊

AI 認為應有訊號，但 TradingView 沒有訊號。

必須追查：

- Raw 是否成立。
- Seed 是否成立。
- 價格承諾是否成立。
- 距離是否超限。
- RR 是否不足。
- 成交量或效率是否未達門檻。
- Session、尾盤、每日上限、冷卻、去重是否阻擋。
- 事件是否已鎖定。
- 是否因資料更新時點造成差異。

### False Positive／假訊

TradingView 有訊號，但 AI 判斷當時不應進場。

必須追查：

- 是否假突破。
- 是否處於族群弱勢或市場逆風。
- 是否融資追價、籌碼發散。
- 是否前方空間不足。
- 是否信號品質門檻過鬆。
- 是否出場機制掩蓋了低品質進場。

### Consensus Signal／共識訊號

AI 認同且 TradingView 有訊號。作為 A 級案例庫，不代表必定獲利，仍需追蹤完整結果。

### Consensus No Signal／共識無訊號

AI 不認同且 TradingView 無訊號。用來衡量引擎避免低品質交易的能力。

## 六、每筆當沖案例必留欄位

使用唯一 ID：

```text
DAY-YYYYMMDD-NNN
```

至少保存：

- 交易日、股票、候選排名。
- Stable 引擎版本。
- AI 預期是否應有訊號。
- TradingView 是否有訊號。
- 多空方向、標籤名稱、時間。
- 進場、出場、報酬、MFE、MAE、出場原因。
- 預期理由。
- 實際阻擋或成立原因。
- 完整 Gate Trace。
- 市場背景。
- 案例權重。
- 檢討與教訓。

重大漏訊或重大假訊可提高案例權重，但不能只因單一重大案例修改策略。

## 七、放寬／收緊測試

每個 Proposal 必須包含：

- 問題。
- 現行規則。
- 樣本區間。
- 樣本數。
- 基準版結果。
- 備案 A、B、C。
- 每個備案的 PF、勝率、平均報酬、MFE、MAE、交易數、漏訊、假訊。
- 改善項目。
- 惡化項目。
- 適用與失效市場。
- AI 建議。
- 風險。
- 等待使用者決定。

若下次遇到相同問題，先查歷史 Proposal：

- 若市場與版本條件相同，優先引用既有結果，答案應保持一致。
- 若市場型態、資料、版本或成本假設不同，必須明確說明差異後重測。
- 不得為了迎合新案例而任意推翻舊結論。

## 八、Stable 版本原則

- 所有 Engine Lab 正式測試一律先取得目前 Stable 版本。
- Candidate 與 Testing 版本不得冒充 Stable。
- 升級 Stable 必須有使用者明確批准紀錄。
- 升級後仍保留舊 Stable 的版本、Commit、樣本與績效。
- 不得覆蓋歷史版本。

## 十、目前技術邊界

- GPT 可透過 MCP 工具把結果寫入 D1，使用者可再從 Dashboard 或查詢工具看到。
- 排程會觸發研究流程，但排程本身不等於能自動操作 TradingView 網頁。
- TradingView 回測資料仍需由可用的 CSV／JSON／Webhook／API 或使用者提供的輸出送入 Engine Lab。
- Fugle 可提供 OHLC 與成交資料，但 Pine 策略訊號仍須由 TradingView 引擎或等價、經驗證的執行環境產生。
- 未取得實際 TradingView 輸出時，不得聲稱已完成正式回測。
